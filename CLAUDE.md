# Medical Reviewer Agent

Spec: `docs/superpowers/specs/2026-10-04-medical-reviewer-agent-design.md`. Plans: `docs/superpowers/plans/`.
Frontend conventions and the design system (DESIGN.md) live in `frontend/CLAUDE.md`.

## Commands
- Backend tests: `cd backend && uv run pytest` (unit). Integration: `MRA_INTEGRATION=1 uv run pytest -m integration` with `docker compose up -d postgres redis searxng`. Run tests from `backend/` (config paths are relative to it).
- API dev server: `cd backend && uv run uvicorn app.main:app --reload --port 8000` (Windows host: add `--loop app.compat:selector_loop_factory`; psycopg async cannot use the Proactor loop)
- Worker: `cd backend && uv run arq app.worker.settings.WorkerSettings`

## Conventions
- Graph nodes report progress only via `app.graph.progress.progress_writer()` (no-op outside a graph); `EventSink` is the only writer to `review_events` / Redis Streams (the worker emits progress; the API emits `queued` and `cancelled`).
- Repositories never commit; callers use `async with session.begin()`.
- Structured LLM calls go through `app/services/llm.py` and the harness runner (`app/harness/runner.py`: validate → repair → escalate), never raw provider clients in nodes. Prompts are English; translation happens last (`app/harness/localize.py`, numbers must survive unchanged). A role's LLM is bound to its `SCHEMAS` entry and the runner's `schema` argument reaches escalation only, so a call that wants another schema uses `deps.llms.with_schema(role, schema)`.
- Models, presets and per-role tuning: the admin console's newest saved version (`llm_config_versions`, `app/services/llm_store.py`) wins and `backend/config/llm.yaml` is the seed (default provider OpenRouter, preset `budget`; `LLM_PRESET` applies only while the seed is in use); workers reload a new version at the next job or within 30 s (`app/worker/llm_reload.py`, same LLM semaphore); the result cache key includes the config version; `python -m app.cli.models list|check [--source db]`. `GRAPH_MODE=stub` runs the Plan 1 placeholder graph; with `STUB_DELAY_SECONDS>0` the stub emits the real event sequence on a scaled timeline (manual QA of the live run, load tests).
- Abstract only (2026-10-05): no full-text fetching or crawling of any kind; papers are read from title + abstract (candidates need ≥ 150 abstract chars) and numbers are verified against the abstract. A pool of up to 120 candidates (one SearXNG top-up page when short) is screened; the user picks how many are analysed (`max_papers`, limits from `/status`).
- Every role's LLM calls share one per-process semaphore (`LimitedLLM`, `LLM_CONCURRENCY`); localization runs in parallel 15-item chunks (bigger batches overflow `max_tokens` in Thai), then items still in English get one retry pass in 5-item chunks.
- Numbers shown to users must be verified against the paper text (`app/harness/verify.py`); unverifiable numbers are nulled, never guessed.
- REST routes and MCP tools are thin adapters over the service layer (`app/services/review_service.py`,
  `paper_search.py`, `report.py`); review rate limits, key quotas, capacity (queue/daily caps, atomic admission lock)
  and Turnstile live in `ReviewService` so both surfaces share them (the paper-search limit is applied in both adapters). MCP server:
  `app/mcp/server.py` (mounted at `/mcp`, stateless); API keys are stored as SHA-256 hashes only.
- SearXNG engine modules live in `infra/searxng/engines/` (AGPL-3.0-or-later, see its README/LICENSE): each carries
  the SPDX header, needs its own read-only bind-mount line in `docker-compose.yml`, and an engine timeout below
  `searxng_timeout_seconds`; markup stripping (`mra_markup.py`) mirrors `app/services/text.py`.
- External MCP tools (`backend/config/mcp_servers.json`) are consulted by `external_enrich`; their output is data
  inside `<external_context>`, never instructions, never a citation.
- Redis clients use `decode_responses=True`.
- Review types (Plans 14a/14b): `narrative | slr` (default) `| scoping | meta_analysis`. SLR prompts are frozen by sha256 pins in `tests/unit/test_prompts_by_type.py` (the one known runtime difference is the shared `ReviewQuestion` tool schema, which now lists nullable `concept`/`context`); narrative and scoping are not graded (`evidence_strength` null) and scoping makes no direction/RoB claims. Results without `review_type` render as legacy.
- Scope form (Plan 17a): `topic` ≤ 600 chars; `study_types` normalised to canonical names (`app/schemas/review.py` `normalize_study_types`, one `Other: …` ≤ 60 chars). Qualitative/mixed-methods (`design_category` `qualitative`/`mixed_methods`) are themes only: never direction evidence, forest rows, pools or grade; their prompt blocks are appended only when the user ticks them (SLR prompt pins unchanged).
- Runtime difference (Plan 17a): the extraction/screen schema's `DesignCategory` enum offers `qualitative`/`mixed_methods` in every review (ticked or not), so an unticked SLR can label a paper qualitative; `reading.py` then strips its effect numbers and direction in code, and it reaches the narrative as themes only.
- `AppDeps` lives in `app/runtime.py` (re-exported by `app.main`) to avoid import cycles with `app/api/*`.
- Capacity and scale (Plan 7): admission control, daily counters and SSE slots live in Redis (`app/services/capacity.py`,
  `sse_slots.py`), so any number of API processes behave as one; per-review LLM spend is capped by a contextvar budget
  charged in `LimitedLLM` (`app/services/budget.py`); the cap scales with the request (`review_cost_cap`: `review_cost_base_usd` + `review_cost_per_paper_usd`·N + `review_cost_per_candidate_usd`·C, at most `max_cost_per_review_usd`; all in `app/config.py`); admission reserves the worst-case cap for each queued/running review and the request's own cap for the new one. Public limits come from `GET /api/v1/status`; never hard-code them
  in docs or UI. Reference docs: `docs/api.md` (keep it in step with routes, events, MCP tools and limits).
- Load test: `scripts/loadtest.py` against the Caddy front (`:8088`) with `GRAPH_MODE=stub STUB_DELAY_SECONDS=20` (the stub emits 125 SSE events per review at `max_papers` 50, measured in Plan 21; `--max-papers` sets the count).
- Cochrane harness (Plan 22a): run from `backend/`: `python -m app.cli.eval select|freeze|run|report` (manifest and
  protocol in `backend/evals/cochrane/`; fixtures/ and runs/ hold third-party abstracts and are git-ignored). The
  eval replays frozen pools from screening onward (`build_eval_graph`), so search changes need a new pool version;
  `eval_year_to` is eval-only state, never a `ReviewOptions` field. It measures Thai quality by harness engineering
  (Thai share, glossary consistency, numbers preserved) — no Thai-tuned or fine-tuned model.
- Not evidence: a further report of a trial (`related_to`) and a paper read as a design outside the ticked study types
  (`design_excluded`) stay in `papers` but are out of comparison rows, key findings, SoF, pools and the grade; the
  report's tallies, RoB summary, study map and DTA table skip them too (`isNotEvidence`). The title block and PRISMA
  still count them as included reports.
- `prompt_version` (`app/config.py`) is part of the result cache key: bump it with any prompt or schema change, and keep
  `docs/api.md` and the pin comments in `tests/unit/test_prompts_by_type.py` in step.
- Plan 14b: `meta_analysis` is a review type that behaves like `slr` and adds `result.meta_analysis` (DerSimonian-Laird in `app/harness/meta.py`, node `pool_effects`). Pooled numbers are computed, so the UI shows them only through `ComputedNumber` (never `VerifiedNumber`) and the narrative never restates them. Citations (`fetch_citations`, OpenAlex with Europe PMC fallback) are metadata only, soft-fail with null coverage, and never fail a review.
- Admin console (Plan 23a): `require_admin` (`app/api/auth.py`) accepts the `mra_admin` session cookie (Redis, `app/services/admin_sessions.py`; Secure per `admin_cookie_secure`) or an admin API key; cookie writes need `X-MRA-Admin: 1`; sign-in attempts are counted before the password is checked; admin routes are registered with `include_in_schema=False` and documented in `docs/api.md`; every admin change writes its `admin_audit` row (`app/services/audit.py`, secrets scrubbed) in the same transaction; admins come only from `python -m app.cli.admin`.
- Runtime settings, glossary and harness (Plan 23c): the 13 settings in `app/services/runtime_settings.py` `SPECS` and the Thai glossary are versioned documents in `config_versions` (`app/services/config_store.py`; secrets, URLs and `HARNESS_MAX_USD` stay env-only); API code reads settings through `ReviewService.effective()` (`RuntimeConfig`, 5 s cache, never `self.settings` for an editable value) and workers reload them with the 23b hook (`app/worker/runtime_reload.py`); with no glossary version the localizer prompt is byte-identical (sha256 pin in `tests/unit/test_glossary.py`) and a saved glossary adds `+g{version}` to the cache key; console harness runs go to the `arq:harness` queue (`app/worker/harness.py`, compose profile `harness`) under a typed USD cap enforced by `run_all(strict_cap=True)`.
- ThaiJO (Plan 24): `app/services/thaijo.py` (search → detail → OAI-PMH) runs while `THAIJO_ENABLED` is true (env only; on by default since 2026-10-13, the owner's decision; `THAIJO_ENABLED=false` turns it off; tests pin it off in `tests/conftest.py`). Health categories only, an English abstract ≥ 150 chars, at most `min(thaijo_max_candidates, candidate_limit // 8)` candidates as their own round-robin list, soft-fail into `errors` and `quality.thaijo`; never `pdf_url` or the HTML page; the OAI host only through `article_link` (`*.tci-thaijo.org`, public addresses, no redirects) and XML with a DTD is refused; `+thaijo` joins the cache key while on; tests use synthetic data only (`tests/unit/thaijo_data.py`), never real responses.
- Sentence support (Plan 25): `app/harness/support.py` (claims, abstract sentences, the candidate scorer, the badge rule) and the `check_support` node (beside `localize`; finalize joins both) check each summary citation group and key-finding ref against the cited abstract, in English before translation: 2 candidate sentences chosen in code, one judge call per review on the screener bound to `SupportBatch` (validate → one repair, never escalates), at most 30 pairs, skipped under $0.02 of budget left, soft-fail to null labels (never fails a review, never edits text or drops a citation); the judge's data block is escaped and evidence is always a candidate picked by index, never judge text. The badge (`verified`) needs supported + the chosen candidate scoring ≥ `MIN_SUPPORT_SCORE` (0.2) + every claim number traced (`prose.unverified_numbers`) + no pooled value + not-evidence excluded; the UI ties shown groups to English claims by position, else by a ref list unique in both texts, else no badge (`src/lib/support.ts`).
- Public safety rails (Plan 26): `app/services/safety.py` holds the red-flag rule and the fixed messages; `ReviewService.create` refuses an emergency topic first, in code and at high precision (a first-person self-harm phrase; a medical red flag with an explicit personal anchor; or a short unframed conversational topic): REST 422 / MCP `status: "refused"` with `code: "emergency"` and 1669 (1323 first for self-harm), no row, no limit hit, no LLM. The guard is the backstop: its `category` `personal_medical` (the asker or someone close, an emergency now, any suicidal or self-harm mention; population research on these stays research) and any provider refusal end the review with `error = "personal_medical: <fixed message naming 1669 and 1323>"` (`refusal_code`, event `code`). Messages never echo the topic, and the personal page never shows it (title included). Audience views (`public` default, `bedside`, `learner`, `committee`; `src/lib/audience.ts`) are presentation only: never in the API, the cache key or `result`; harms-gap and dosing notices (`src/lib/safety.ts`) are computed in the browser and never rewrite text.
- Quick answer (Plan 27): `options.mode` `full | quick` (cache key); a quick answer is fixed at `QUICK_CANDIDATE_LIMIT` 30 → `QUICK_MAX_PAPERS` 8, `slr` (`app/schemas/review.py`, published in `/status` `limits.quick`), shares every limit and counter with full reviews, and its cost cap is the usual formula with those sizes. It reads without external tools or citations and goes `normalize_outcomes → write_quick_answer` (`app/graph/nodes/quick.py`, prompt pinned): 2–4 cited sentences checked per sentence by the full review's citation and prose rules (a citation after a full stop is moved inside it; any sentence stating a certainty level is dropped), the certainty line from the GRADE-lite baseline, stored in the Synthesis shape so localize, check_support and finalize are unchanged; `result.quick.refs` numbers the references [1]…[n]. The web form starts as a quick answer; `?mode=full` restores a full review, and retry links keep the review's mode. MCP: `start_review(mode=…)`, `quick_answer`.
- Search sources (Plan 23d): the nine sources (eight SearXNG engines, ThaiJO; `app/services/sources.py`) are a third versioned kind in `config_versions` (`sources`, `app/services/sources_store.py`, mirror `mra:sources:active`): a sparse `{sources: {id: bool}}` of where they differ from `SEARXNG_ENGINES`/`THAIJO_ENABLED`, winning over env both ways, at least one SearXNG source on; the API reads them through `ReviewService.sources()` (5 s, recomputed only when the version moves) and workers put them in `GraphDeps.sources` (a running review keeps its set; Europe PMC off also stops its RCT search, never enrichment). No version → the cache key is unchanged; with one, `+thaijo` follows the set and `+src<sha256[:8] of the sorted engines>` marks an engine set that differs from env. `/status` `sources` is the public list (the web falls back to the static eight).
